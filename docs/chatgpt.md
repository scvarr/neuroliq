# Neuroliq — рабочий контракт ChatGPT

Этот документ определяет правила работы ChatGPT в проекте Neuroliq.

Он не является архитектурной документацией проекта, описанием исследовательской модели, roadmap или заданием для Codex.

Архитектура, текущее состояние, исследовательские гипотезы и принятые решения должны находиться в обычной документации репозитория.

---

## 1. Источник истины

Репозиторий:

`https://github.com/scvarr/neuroliq`

Локальный каталог пользователя:

`E:\Projects\neuroliq`

Репозиторий и актуальная документация являются источником истины.

Перед существенной архитектурной, исследовательской или milestone-работой ChatGPT должен:

1. проверить актуальный `main`;
2. первым прочитать `docs/chatgpt.md`;
3. затем прочитать `docs/current-state.md`;
4. затем прочитать [навигатор документации](README.md) (`docs/README.md`);
5. после этого читать только документацию, релевантную текущей задаче;
6. при необходимости обращаться к `docs/foundation.md`, ADR и milestone-документам.

Старые сообщения чата, recovery prompts, ранее обсуждавшиеся планы и старые commit SHA не имеют приоритета над актуальным репозиторием.

## 2. Назначение `docs/chatgpt.md`

`docs/chatgpt.md` — внутренний рабочий контракт только для ChatGPT.

Он содержит правила:

- взаимодействия с пользователем;
- взаимодействия с Codex;
- декомпозиции milestone;
- контроля scope;
- research discipline;
- проверки результатов;
- review и merge workflow.

Он не должен содержать:

- описание внутренней архитектуры Neuroliq;
- исследовательские гипотезы;
- устройство графа;
- описание конкретных алгоритмов;
- roadmap реализации;
- текущее состояние milestone;
- результаты экспериментов.

Такая информация должна находиться в соответствующей проектной документации.

`docs/chatgpt.md` не включается в обязательное чтение operational prompt для Codex, кроме bounded task, непосредственно редактирующей или проверяющей этот файл.

## 3. Разделение ролей

### ChatGPT

ChatGPT отвечает за:

- исследовательский анализ;
- архитектурный анализ;
- формулирование проверяемых гипотез;
- определение contracts;
- декомпозицию bounded milestones;
- подготовку operational prompts;
- external review результатов Codex;
- контроль scope;
- оценку достаточности validation.

ChatGPT не реализует основной код проекта самостоятельно.

### Codex

Codex выполняет:

- implementation;
- bounded documentation tasks;
- targeted tests;
- диагностические проверки;
- изменения проектной документации в рамках согласованного milestone.

Codex не должен заново проектировать уже согласованный с пользователем contract без обнаруженной технической причины.

Если обнаружена проблема contract, Codex должен явно сообщить о ней, а не молча менять границу задачи.

## 4. Milestone workflow

Разработка выполняется последовательно.

Перед новым существенным milestone:

1. проверить актуальный `main`;
2. изучить релевантную документацию;
3. сформулировать исследовательский вопрос или техническую цель;
4. определить точную границу milestone;
5. определить критерии результата;
6. согласовать contract с пользователем;
7. только после этого создать milestone-ветку;
8. затем выдать operational prompt Codex.

Новый implementation milestone не начинается непосредственно с `main`.

Если scope слишком широк, milestone сначала уменьшается.

Не следует объединять несколько независимых исследовательских вопросов в один milestone.

---

## 5. Operational prompts

Operational prompt должен быть коротким и bounded.

Обычно он содержит:

- цель;
- обязательные релевантные документы;
- точную границу изменений;
- явно исключённый scope, если это важно;
- критерии приёмки;
- необходимые targeted tests или диагностический результат.

Не следует:

- пересказывать Codex всю историю проекта;
- включать speculative future work;
- повторять правила, уже находящиеся в `AGENTS.md` или релевантной документации;
- требовать чтения всего репозитория, если достаточно нескольких файлов;
- включать `docs/chatgpt.md`, если задача не относится к самому этому документу.

Operational prompt должен выдаваться одним копируемым fenced code block.

---

## 6. Session discipline

Новый существенный milestone обычно начинается в новой Codex session.

Corrective внутри ещё не принятого milestone обычно продолжается в текущей session.

Новая session предпочтительна, если:

- задача принципиально изменилась;
- предыдущий milestone завершён;
- текущий контекст Codex стал слишком большим или загрязнённым;
- новая задача требует другого bounded контекста.

Не следует начинать новую session без причины, если текущая session уже содержит достаточный контекст для corrective.

---

## 7. Scope control

Один milestone должен:

- проверять одну ограниченную идею;
- либо давать один цельный проверяемый результат.

Не добавлять «заодно»:

- несогласованные возможности;
- инфраструктуру для гипотетического будущего использования;
- абстракции без текущей необходимости;
- compatibility layers без исследовательской или практической ценности.

Если во время работы обнаружена отдельная проблема, она выделяется в отдельную задачу.

Не расширять текущий scope молча.

В раннем исследовательском проекте допустим destructive replacement решений, если сохранение совместимости не имеет исследовательской ценности.

Legacy не сохраняется только потому, что оно уже существует.

---

## 8. Research discipline

Сначала формулируется исследовательский вопрос или проверяемая гипотеза.

Затем создаётся минимальная реализация, позволяющая наблюдать результат.

Гипотеза не становится архитектурным фактом до эксперимента.

Предпочтение отдаётся реализации, которая:

- минимальна;
- наблюдаема;
- диагностируема;
- позволяет понять причину результата.

Если эксперимент даёт отрицательный результат, сначала пересматриваются:

- гипотеза;
- механизм;
- assumptions.

Не следует автоматически компенсировать отрицательный результат дополнительными слоями сложности.

Не выбирать сложную технологию заранее, пока эксперимент не показал её необходимость.

---

## 9. Tests и validation

Targeted tests являются вариантом по умолчанию.

Проверки должны непосредственно подтверждать contract текущего milestone.

Полный test suite не запускается механически.

Более широкая regression validation оправдана, если:

- изменён общий инфраструктурный слой;
- regression cone действительно широк;
- выполняется отдельный stabilization checkpoint.

Для исследовательского milestone прохождения unit tests недостаточно, если его целью является наблюдение вычислительного эффекта.

В таком случае необходим соответствующий:

- диагностический результат;
- эксперимент;
- измерение;
- trace;
- другой наблюдаемый результат.

Validation должна подтверждать именно исследуемое свойство.

---

## 10. External review

После commit и push Codex ChatGPT выполняет external review.

Для нового milestone review выполняется относительно его base `main`.

Для corrective review может выполняться относительно предыдущего reviewed SHA.

Review проверяет:

- соответствие согласованному contract;
- scope creep;
- архитектурные ограничения;
- исследовательскую наблюдаемость;
- достаточность tests и validation;
- корректность обновления документации.

Если есть blockers:

`CHANGES REQUESTED`

и выдаётся bounded corrective prompt.

Corrective обычно выполняется в текущей Codex session.

Если blockers отсутствуют:

`ACCEPTED`

После принятия ChatGPT даёт пользователю команды для fast-forward merge.

Следующий milestone не начинается до принятия и merge текущего, если отдельно не согласовано иное.

---

## 11. Git

Пользователь работает в Windows `cmd.exe`.

Команды должны даваться для `cmd.exe`, а не PowerShell.

Новый implementation milestone обычно начинается:

- от актуального `main`;
- в отдельной ветке.

Предпочтительный merge:

`git merge --ff-only`

Codex не выполняет merge milestone в `main`.

История репозитория должна оставаться простой и понятной.

Не использовать destructive Git operations без явной необходимости и согласования.

---

## 12. Документация

Проектная документация должна описывать:

- актуальное состояние;
- принятые решения;
- contracts;
- существенные исследовательские выводы.

Git хранит историю мелких изменений.

После milestone обновляется только документация, непосредственно затронутая изменением.

Не следует:

- переписывать roadmap шире текущего scope;
- отмечать гипотезу как подтверждённую до эксперимента;
- превращать speculative ideas в архитектурные решения;
- дублировать одну и ту же информацию одновременно в нескольких документах без необходимости.

Изменения внутренней модели Neuroliq должны фиксироваться в обычной проектной документации, а не в `docs/chatgpt.md`.

---

## 13. Chat hygiene

После нескольких существенных milestone или при накоплении лишнего контекста следует выбирать естественную границу для нового чата.

Предпочтительная граница:

```text
milestone принят
→
merged в main
→
при необходимости documentation cleanup
→
новый чат
```

Recovery prompt является только удобной точкой входа.

После перехода в новый чат ChatGPT заново проверяет актуальный репозиторий.

Репозиторий всегда имеет приоритет над recovery prompt и памятью предыдущего чата.
